# Provider-observed TLS evidence

This note defines the evidence boundary and human acceptance gate for TLS / ClientHello work. It exists to prevent local diagnostic evidence from being reported as provider-observed proof.

Current T044 status: `DONE_HEALTHY_CODEX_PRO_WEBSOCKET_SUCCESS_WITH_REMOTE_PROXY`, not `DONE_PROVIDER_SIDE_TLS_PARITY`. The remote core now has first-hand, sanitized SOCKS proxy-tunnel pcaps for Codex A02, including parsed ClientHello entries with SNI `chatgpt.com`, ALPN `h2,http/1.1`, and JA3 evidence. After A02 hit provider quota, T044 also synced a local healthy Codex Pro account as access-token-only, kept refresh disabled, forced it through the remote-valid account proxy, and completed a real WebSocket `GET /v1/responses` request with upstream `200` and output `OK`. This closes client-side core-mediated authenticated egress for the selected account/proxy/fingerprint path, but it still does not prove provider-side edge observation or provider-side JA3/JA4 parity.

## Evidence tiers

| Tier | Evidence type | What it proves | What it does not prove | Completion meaning |
| --- | --- | --- | --- | --- |
| 1 | `synthetic-provider-sni` | A local listener captured ClientHello / JA3 / JA4 / ALPN / HTTP2 behavior emitted by the runtime/profile builder while the request URL/SNI used a provider host such as `api.anthropic.com` or `chatgpt.com`. | The provider did not observe this flow. It does not prove provider edge behavior, proxy-chain preservation, or authenticated account runtime parity. | Safe local diagnostic evidence only. |
| 2 | `account-runtime` | The core resolved account runtime state for a fixture/request window: managed header source/version, `refresh_enabled`, transport profile, TLS profile, and HTTP-version policy. | It does not prove JA3 / JA4, encrypted HTTP/2 SETTINGS, provider edge behavior, or that a real provider request used the same TLS handshake. | Runtime-resolution evidence only. |
| 2.5 | `core-mediated-provider-tls-pcap` | The running CLIProxyAPIPlus core resolved the account runtime/profile and initiated a no-Authorization outbound TLS probe to the provider host while a scoped pcap captured either provider host:443 or the configured HTTP proxy tunnel endpoint. | It is still not a full authenticated provider request, does not send provider Authorization, and normal pcap cannot reveal encrypted HTTP/2 SETTINGS. A proxy-endpoint pcap proves core-to-proxy tunnel traffic, not provider-edge observation. | Stronger than openssl direct-connect because TLS is initiated by core, but still below full provider-observed authenticated parity. |
| 2.7 | `core-mediated-authenticated-api-call-pcap` | The management `api-call` path selected a specific `auth_index`, substituted the provider token, used account proxy settings, and reached the real upstream while a sanitized pcap captured the SOCKS tunnel and ClientHello. | It can still return provider `401 token_expired`; it does not prove a successful model response, provider-side JA3/JA4 observation, or encrypted HTTP/2 SETTINGS. It also does not prove the main `/v1/responses` executor selected the same account unless that executor path is separately captured. | Client-side authenticated egress closure for the selected account/proxy path. |
| 3 | `provider-observed TLS` | A provider-facing or provider-side source observed the actual provider-host flow and can correlate host, timestamp, runtime/account/profile, and observed TLS fields. | Plain pcap may still not reveal encrypted HTTP/2 SETTINGS; MITM may prove client-to-MITM behavior rather than provider-observed ClientHello unless explicitly paired with provider-side proof. | Only this tier can close provider-observed TLS evidence without waiver. |

The first two tiers can support a human waiver, but they must not be renamed or summarized as provider-observed TLS.

Tier 2.5 can support a stronger waiver or a scoped provider-host pcap review because the flow is generated by the core process and the same account runtime resolver. It must still be labeled `core-mediated-provider-tls-pcap`, not full authenticated provider-observed TLS.

Tier 2.7 can close the practical client-side egress question for an account: the selected account proxy, provider token substitution, provider host, and TLS ClientHello are all exercised by the running remote core. It must still be labeled as client-side / core-mediated evidence because the provider has not supplied its observed fingerprint and normal pcap cannot expose encrypted HTTP/2 SETTINGS.

## Core-mediated pcap evidence

This path is the preferred semi-automated T034b workflow when an authorized operator can run a scoped remote capture but AI/local automation should trigger and analyze the diagnostic evidence.

### Core diagnostic endpoint

The core exposes a management diagnostic action:

- Endpoint: `POST /v0/management/diagnostics/provider-tls-probe`
- Body:

```json
{
  "name": "codex-a02.json",
  "provider": "codex",
  "target_host": "chatgpt.com",
  "method": "HEAD",
  "path": "/",
  "correlation_id": "core-provider-tls-YYYYMMDDTHHMMSSZ"
}
```

Provider target hosts are intentionally allowlisted:

- Claude: `api.anthropic.com`
- Codex: `chatgpt.com`

The diagnostic probe:

- selects the auth/account by management auth name or auth ID
- resolves account runtime evidence through the same managed-header, transport-profile, TLS-profile, proxy, and HTTP-version resolver used by runtime code
- sends a harmless `HEAD` or `GET` request from the core process to the provider host only after a supported account runtime transport/profile or the core default runtime transport path is available
- sets only diagnostic headers such as `X-CLIProxyAPI-Diagnostic-Correlation-ID`
- never sends `Authorization`, `Bearer`, provider auth headers, access tokens, refresh tokens, cookies, or API keys
- never accepts a plain `http.DefaultTransport` override or unsupported explicit runtime profile
- fails with `runtime_transport_required` before opening a provider connection when no executable runtime transport can be built
- allows provider `401`, `403`, `404`, network errors, or TLS errors; the goal is timestamp/correlation and TLS initiation, not provider success

The response records:

- `correlation_id`
- provider and target host
- account/auth hashes only
- outbound URL and timestamp window
- `core_build_headers` from `X-CPA-*` build metadata
- `account_runtime_evidence_sha256` and `account_runtime_summary`
- HTTP status or network error
- `authorization_sent=false`
- `runtime_profile_enforced=true` and `transport.runtime_profile_enforced=true` only when the request was sent through the runtime-profile transport
- `runtime_profile_source`, such as `explicit_account_profile` or `core_default_runtime`
- `provider_observed=false`
- `secret_values_stored=false`

### Human/operator capture wrapper

Use the wrapper from the repository root:

```bash
scripts/core-mediated-provider-tls-capture.sh \
  --provider codex \
  --auth-name codex-a02.json \
  --management-url https://10.1.1.201:18317 \
  --trigger \
  --dry-run
```

In an approved remote maintenance/capture window, the operator runs the same script with `sudo`, `MANAGEMENT_PASSWORD` in the environment, and `--execute`:

```bash
sudo MANAGEMENT_PASSWORD='<not printed>' scripts/core-mediated-provider-tls-capture.sh \
  --provider claude \
  --auth-name claude.json \
  --management-url https://10.1.1.201:18317 \
  --trigger \
  --insecure \
  --execute
```

The script:

- creates a capture directory under `build/provider-observed-tls/core-mediated/<correlation-id>/` unless `--out-dir` is supplied
- resolves the provider host before capture
- starts tcpdump with a filter scoped to resolved target host IPs and port `443`, or to an explicitly supplied proxy host/port when `--capture-endpoint proxy` is used
- either triggers the core diagnostic endpoint itself or waits for another local/AI trigger during the capture window
- stops tcpdump and writes `manifest.json`
- scans generated text artifacts and pcap strings output for token-like markers, including `Proxy-Authorization`
- sanitizes proxy endpoint captures by default by removing packets that contain proxy/auth token markers before writing the shareable pcap
- never prints or saves `MANAGEMENT_PASSWORD`

This path is stronger than `scripts/provider-observed-tls-capture.sh --mode pcap-handshake` because the TLS flow is initiated by the deployed core process and correlated to the account-runtime evidence hash. It is still intentionally unauthenticated; do not claim that a real provider Authorization request, provider auth header behavior, or provider-side account acceptance has been verified.

If the deployed core uses an HTTP upstream proxy, a provider-host filter can legitimately produce an empty 24-byte pcap even when `probe-response.json` shows `http_status` and `runtime_profile_source=core_default_runtime`. In that case, first prefer `runtime-egress`, which captures both provider `:443` and the proxy tunnel endpoint in the same short window without putting proxy credentials on the command line:

```bash
sudo MANAGEMENT_PASSWORD='<not printed>' scripts/core-mediated-provider-tls-capture.sh \
  --provider codex \
  --auth-name codex-a02.json \
  --management-url https://10.1.1.201:18317 \
  --trigger \
  --insecure \
  --capture-endpoint runtime-egress \
  --capture-host 10.1.1.5 \
  --capture-port 7890 \
  --interface any \
  --execute
```

Proxy tunnel evidence must be labeled as proxy-tunnel or runtime-egress pcap. Do not share a raw proxy pcap when the proxy URL contains credentials; keep the default sanitization enabled unless the reviewer has a separate secure retention plan.
Use `--interface any` for Dockerized remote cores when a specific physical interface such as `ens34` produces `0 packets captured`; it captures across bridge/veth/egress interfaces while retaining the host/port filter.

When an account has its own `proxy_url`, it overrides the global proxy. Capture the account proxy endpoint, not the global proxy endpoint. For SOCKS proxies with credentials, use a temporary external marker file for pcap sanitization so packets containing username/password markers are removed before the artifact is shared. The marker file must not be copied into the artifact, printed, or referenced in the manifest.

### Community-backed provider-side MVP path

Community projects suggest a practical controlled-observation MVP:

- Use a TLS fingerprint echo or reverse proxy such as `wi1dcard/fingerproxy` or `0x4D31/finch` to return JA3, JA4, Akamai / HTTP/2 fingerprint fields, and request metadata.
- Use a client-fingerprint implementation reference such as `Noooste/azuretls-client` only as a client-generation reference, not as proof that a real provider saw the same fingerprint.
- For Claude, keep using Claude-specific policy and Anthropic's documented network boundaries. Anthropic documents proxy / CA / mTLS / network configuration, and reviewed Claude-related open-source projects expose useful app-layer client/proxy patterns, but none of them provide an official Claude Code JA3 / JA4 / HTTP/2 SETTINGS baseline.
- The current Claude canonical preset is `claude_utls_chrome_133`; old `claude_chrome_like_mac_v3` and `chrome_133` values are compatibility aliases, not a stronger TLS parity claim. Chrome-like uTLS is an explicit advanced opt-in; `provider-default` does not automatically enable it for Claude.
- Core-managed CLI-native runtime identity is now automatic for Claude / Codex / Gemini accounts. It proves account-scoped runtime isolation only; it is not browser impersonation and not provider-edge TLS parity.
- T056 adds persistent `runtime_identity_state` to account settings, so the core-generated identity has a stable `identity_id`, revision, hashed seed/account/proxy fields, and append-only history. This improves auditability of account isolation, but still does not convert controlled echo evidence into provider-edge TLS parity.
- Correlate any echo result with the core request log: provider-like host or controlled domain, account label, runtime profile, managed header version, UTC timestamp window, request ID/correlation ID, and redaction boundary.

This MVP can close a controlled provider-facing fingerprint evidence gate. It still must not be relabeled as real provider-side TLS parity unless the observation point is the actual provider edge or a provider-approved echo/log source.

### T045 controlled fingerprint echo MVP

T045 implements the controlled-observation path as a management diagnostic extension:

- The core diagnostic endpoint keeps `Authorization` and provider credentials disabled for the outbound request.
- Provider defaults remain restricted to the real provider hosts (`api.anthropic.com` for Claude, `chatgpt.com` for Codex).

## Account-runtime evidence

`account-runtime` evidence is a separate, weaker-but-safe evidence class. It proves what the core resolves from an auth/account fixture at request time, without reading tokens and without sending an authenticated provider request.

The safe helper is:

- `third_party/CLIProxyAPIPlus/internal/runtime/executor/helps.BuildAccountRuntimeEvidence`
- `third_party/CLIProxyAPIPlus/internal/runtime/executor/helps.BuildAccountRuntimeEvidenceJSON`
- `third_party/CLIProxyAPIPlus/internal/runtime/executor/helps.LogAccountRuntimeEvidence`

The emitted schema is intentionally redacted:

- `evidence_type`: always `account-runtime`
- `claim_scope`: `runtime-resolution-not-provider-observed`
- `timestamp` and `correlation_id`: used to correlate with a request/log window
- `provider`, `base_url_host`, `refresh_enabled`
- `managed_headers`: policy version, source/source URL/checked time, version, strategy, header names, and SHA-256 value hashes only
- `transport_profile`, `tls_profile`, `http_version`: resolved profile IDs, fallback status, ALPN / HTTP/1.1 policy, and runtime-enforcement flags
- `provider_observed`: always `false`
- `secret_values_stored`: always `false`

This evidence can prove that the remote core would choose `codex-managed/v2`, `Version=0.125.0`, `refresh_enabled=false`, `transport_profile=provider-default`, or `tls_profile=current-fallback` for a given account fixture. It cannot prove JA3 / JA4, encrypted HTTP/2 SETTINGS, provider edge behavior, or that a real authenticated provider request used the same TLS handshake.

## Acceptance / waiver gate

Use one of these dispositions:

- `ACCEPTED_PROVIDER_OBSERVED`: first-hand provider-observed TLS evidence exists and satisfies the checklist below.
- `READY_FOR_HUMAN_WAIVER`: provider-observed evidence is missing, but the remaining risk can be explicitly accepted by a human reviewer based on lower-tier evidence.
- `BLOCKED_ON_PROVIDER_OBSERVED_TLS`: neither first-hand evidence nor an explicit waiver exists.

### Waiver can be acceptable

A waiver is acceptable only when all of the following are true:

- Synthetic provider-SNI evidence exists for the relevant provider/profile and is clearly labeled `synthetic-provider-sni`.
- Account-runtime evidence exists for the relevant account/provider and is clearly labeled `account-runtime`.
- Remote deployment proof exists for the runtime under review, including matching `X-CPA-*` headers or an equivalent deployment manifest.
- The release note, handoff, or review record explicitly says provider-observed TLS is waived, not completed.
- The reviewer accepts the residual risk that provider edge behavior, proxy-chain preservation, and encrypted HTTP/2 SETTINGS are not proven.
- The waiver scope is bounded by provider, account label, runtime version/manifest, date, and rollback/disable plan.

### First-hand evidence is still required

Do not use a waiver when any downstream claim or decision depends on provider-observed parity. First-hand evidence is required when:

- claiming provider-observed TLS, JA3, JA4, ALPN, HTTP/2 SETTINGS, or provider-edge fingerprint parity is complete
- promoting a change where account identity risk must be proven against provider-facing traffic rather than local runtime intent
- investigating provider-originated `401` / `403` / `404` / `429`, anti-abuse, or fingerprint mismatch behavior
- changing TLS/profile behavior after the lower-tier evidence was generated
- the reviewer cannot accept the residual risk in writing

## Human-run capture checklist

This section is a checklist for an authorized human-run validation. It intentionally does not provide privileged capture commands, MITM setup instructions, or steps for observing unrelated traffic.

### Safety premises

- Use only machines, networks, accounts, and traffic that the operator is authorized to inspect.
- Run in an isolated development or approved maintenance window; do not mix with production user traffic.
- Scope the observation to one provider host, one account label, one runtime version, and a short time window.
- Do not read, print, or store access tokens, refresh tokens, cookies, API keys, Authorization headers, or full request/response bodies.
- Store only redacted summaries by default; if raw artifacts are retained, record access controls, retention time, and hashes.
- If the method cannot avoid capturing unrelated traffic, do not use it for this repository gate.

### Required inputs

- Provider and exact host, for example `anthropic/api.anthropic.com` or `codex/chatgpt.com`.
- Runtime under test: local/remote, build commit, version headers, and deployment manifest path.
- Account label or fixture label; never include raw token material.
- Expected profile labels: managed header profile, transport profile, TLS profile, and HTTP-version policy.
- Correlation ID and UTC timestamp window.
- Capture source type: provider-side log, provider echo, scoped pcap summary, or other approved first-hand source.
- Redaction plan and artifact retention owner.

### Required outputs

- A redacted manifest that records provider host, timestamp window, runtime version, account label, correlation ID, and capture source.
- A summary of observed fields: SNI, ALPN, JA3, JA4, TLS version, HTTP version, and HTTP/2 SETTINGS if actually visible.
- A statement of fields not observable, especially encrypted HTTP/2 SETTINGS in normal TLS.
- SHA-256 hashes for retained evidence artifacts, if any.
- A token boundary statement: `authorization_absent`, `authorization_redacted`, or `not_applicable`.
- A final disposition: `ACCEPTED_PROVIDER_OBSERVED`, `READY_FOR_HUMAN_WAIVER`, or `BLOCKED_ON_PROVIDER_OBSERVED_TLS`.

## Claim gate

Do not mark provider-observed TLS as complete unless evidence includes all required correlation:

1. exact provider host and timestamp
2. selected runtime/profile and account label that generated the traffic
3. capture source: provider-side log, provider echo, scoped pcap summary, or another approved first-hand source
4. token boundary: Authorization absent, not used, or redacted before storage
5. explicit statement whether HTTP/2 SETTINGS are actually observed or unavailable due to TLS encryption
